Esto es una ayuda y un ejemplo, no una receta obligatoria.

Cada skill puede variar según la necesidad del proyecto, la arquitectura, las tecnologías y el agente que use el equipo. Adapta el prompt, la plantilla, la ubicación y las verificaciones a tu contexto.

Qué debería dejar claro un skill

  • Qué trabajo ayuda a completar y cuándo usarlo.
  • Qué contexto necesita y qué resultado produce.
  • Qué verificaciones realiza y qué decisiones corresponden a una persona.
  • Qué ejemplo explica su uso en el repositorio.

Los seis ejemplos siguientes se enfocan en el flujo de trabajo y no dependen del stack. Los skills de backend, frontend, datos e IA se definen cuando el proyecto ya eligió su arquitectura y tecnologías.

Ideas útiles para el flujo del equipo

  • Usa el plan aprobado como referencia para revisar el cambio. Si la implementación se aparta del alcance o de la solución acordada, documenta y justifica el ajuste en el artefacto que ya usa el equipo.
  • Organiza el code review en pasadas: comportamiento y regresiones; seguridad y privacidad; cumplimiento del plan, criterios y políticas del proyecto. Prioriza hallazgos accionables y evita repetir checks que CI ya cubre o llenar el reporte con preferencias de estilo.
  • Un skill guía el trabajo, pero no garantiza una regla por sí solo. Para controles obligatorios, define verificaciones automáticas y protecciones del flujo; la aprobación del PR permanece en las personas responsables.
  • Más adelante, si los skills se vuelven parte crítica del delivery, prueba sus cambios con tareas representativas y resultados esperados. No es un requisito para empezar.
Skill 1

Set Up and Validate the Monorepo

Objetivo: establecer la estructura del repositorio y el contexto persistente del agente; comprobar que esté el archivo de instrucciones aplicable (AGENTS.md para Codex, CLAUDE.md para Claude Code, o ambos si el equipo usa ambas herramientas) junto con los demás elementos acordados.

Prompt para crearlo

Crea un skill llamado “Set Up and Validate the Monorepo”. Usa la estructura de referencia y las instrucciones vigentes del repositorio. El archivo de contexto del agente es esencial: AGENTS.md cuando el equipo use Codex, CLAUDE.md cuando use Claude Code, y ambos si acuerda usar las dos herramientas. El skill debe ayudar a crear y validar ese archivo, comprobando que describa el propósito del proyecto, el mapa del repositorio, comandos de desarrollo y validación, convenciones, dónde leer el plan aprobado y qué decisiones requieren revisión humana. Después valida las demás carpetas y archivos aprobados; clasifica cada uno como presente, ausente, incompleto o no aplica. No debe exigir documentos que solo aparezcan en ejemplos ni crear un archivo Markdown para cada tema. Si se solicita inicializar, debe crear solo los elementos aprobados que falten y no sobrescribir archivos sin autorización. Al crear este skill, crea únicamente su archivo; no inicialices ni modifiques el monorepo.

Plantilla: esqueleto neutral

/
├── README.md
├── AGENTS.md       # si el equipo usa Codex
├── CLAUDE.md       # si el equipo usa Claude Code
├── apps/
│   └── [aplicación o servicio elegido]
├── packages/
│   └── [paquetes compartidos, si se necesitan]
├── docs/
│   └── [artefactos definidos por el flujo del proyecto]
├── [directorio de skills del agente elegido]
└── .github/
    ├── workflows/                  # si se usa GitHub Actions
    ├── CODEOWNERS                   # si se definen propietarios
    └── pull_request_template.md     # si el equipo adopta una plantilla

Skill 2

Create a Feature Plan

Objetivo: analizar una solicitud y producir un plan revisable con el formato del equipo, antes de comenzar a codificar.

Prompt para crearlo

Crea un skill llamado “Create a Feature Plan”. Inspecciona los planes y plantillas aprobados y sigue la convención del equipo. Analiza el requerimiento y el repositorio: objetivo, alcance, criterios verificables, patrones existentes, componentes afectados, contratos, dependencias, riesgos, alternativas, validación y reversión cuando aplique. Separa hechos, supuestos y preguntas abiertas; no inventes decisiones ni escribas código. Deja el resultado en borrador para revisión humana. Al crear este skill, crea únicamente su archivo y no un plan de funcionalidad real.

Skill 3

Record an ADR

Objetivo: documentar una decisión, las opciones consideradas y sus consecuencias en el lugar y formato que acuerde el equipo.

Prompt para crearlo

Crea un skill llamado “Record an ADR”. Localiza la ubicación y la plantilla de ADR acordadas; si no existen, propone una plantilla y pide al equipo aprobar la ubicación antes de crear un ADR. Inspecciona los ADRs existentes para seguir su numeración, formato y estados. El skill debe ayudar a describir contexto, criterios, opciones, trade-offs, decisión, consecuencias, validación y referencias. Debe mantener la diferencia entre propuesta y decisión aceptada; no inventar consenso ni marcar una decisión como aceptada sin aprobación. Al crear este skill, crea únicamente su archivo; no registres un ADR real.

Skill 4

PR Code Review

Objetivo: analizar el diff frente al objetivo y al comportamiento esperado para identificar defectos, regresiones o riesgos con evidencia concreta.

Prompt para crearlo

Crea un skill llamado “PR Code Review”. Sigue las convenciones del repositorio y usa el formato de reporte de abajo. Compara el diff con el objetivo, el plan aprobado y los criterios de aceptación. Revisa en pasadas separadas el comportamiento, los casos límite y las regresiones; la seguridad y privacidad; y el cumplimiento del plan, contratos y políticas del proyecto. Lee suficiente contexto de los archivos afectados. Reporta hallazgos accionables con área, prioridad, ubicación, evidencia, impacto y corrección o validación sugerida. No repitas hallazgos que CI ya cubre y limita las observaciones de estilo a las que tengan impacto real. Si no encuentra defectos, indícalo y resume el alcance revisado. Registra los checks observados sin afirmar resultados que no tengan evidencia. El skill produce hallazgos y recomendaciones: no modifica archivos, no publica comentarios ni aprueba o fusiona el PR. Al crear este skill, crea únicamente su archivo; no revises un PR real.

Nota: adapta prioridades, alcance y reporte al riesgo y a las reglas de revisión del proyecto. El skill entrega hallazgos y recomendaciones; no modifica código ni publica comentarios.

Skill 5

PR Triage

Objetivo: atender comentarios de revisión e issues asociados al PR, distinguiendo correcciones, preguntas, preferencias y temas ya resueltos.

Prompt para crearlo

Crea un skill llamado “PR Triage”. Usa las convenciones del repositorio y el formato de reporte de abajo. Consulta el contexto y evidencia relevante para cada comentario o issue; clasifica cada punto y propone una corrección o respuesta precisa. Antes de modificar código, presenta la corrección y espera autorización. Después de un cambio autorizado, prepara una respuesta por comentario con evidencia; publícala solo cuando el usuario lo solicite. No apruebes ni fusiones el PR. Al crear este skill, crea únicamente su archivo; no atiendas un PR real.

Skill 6

Create a PR

Objetivo: preparar un PR que explique el cambio, enlace el trabajo relacionado y muestre qué validaciones se ejecutaron.

Prompt para crearlo

Crea un skill llamado “Create a PR”. Inspecciona la plantilla de PR, las convenciones de ramas, los checks requeridos y las instrucciones del repositorio. Usa la plantilla que aparece abajo solo si el repositorio no tiene otra acordada. Revisa el diff frente al plan aprobado y señala cualquier cambio de alcance o desviación que deba documentarse. El skill debe revisar el estado de Git, relacionar el PR con el plan, issue y ADR cuando correspondan, y resumir propósito, cambios, validaciones reales y riesgos. Debe distinguir validaciones aprobadas, fallidas, pendientes y no ejecutadas; nunca afirmar que una prueba pasó sin evidencia. Crea el PR solo cuando el usuario lo solicite y nunca lo fusiones. Al crear este skill, crea únicamente su archivo; no abras un PR real.

Plantilla de descripción del PR

## Propósito
¿Qué problema resuelve este cambio?

## Cambios incluidos
- ...

## Referencias
- Issue:
- Plan aprobado:
- ADR relacionado:

## Validación
- [ ] <comando o check ejecutado> — resultado:
- [ ] <prueba manual o evidencia, si aplica>
- No ejecutado / pendiente:

## Riesgos e impacto
- ...

## Checklist del autor
- [ ] El alcance corresponde al plan aprobado.
- [ ] La documentación y los contratos afectados están actualizados.
- [ ] Los checks reportados corresponden a ejecuciones reales.
- [ ] No se incluyeron secretos ni datos sensibles.

Nota: adapta el título, campos y checklist a la plantilla del repositorio. Crear un PR no autoriza a fusionarlo.

Cómo mantener la documentación útil

  • Mantén una fuente de verdad por artefacto y enlaza documentos relacionados.
  • Usa encabezados claros y enlaces relativos para facilitar la navegación en GitHub.
  • Crea documentos y plantillas cuando un flujo real los necesite; no por tener una carpeta vacía que llenar.

Las plantillas son puntos de partida. Cada equipo puede adaptar el contenido y el nivel de detalle según las necesidades y reglas de su proyecto.
