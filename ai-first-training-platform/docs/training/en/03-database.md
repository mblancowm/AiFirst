# 03 · Store and look up data

> Week 2 · 2 hours · Main focus: data

The database keeps application information. For the minimum scope, start with one table for one type of record. The API saves those records and returns the list; updating and deleting are optional.

## Before you start: data as a spreadsheet

A **table** is like a spreadsheet: each row is one record and each column stores one piece of information. For example, an articles table might have a title and content. The minimum app needs one table; it does not need relationships between tables.

Drizzle describes tables in code and SQLite stores the data. A **migration** is a recipe for changing the database structure in an orderly way. Ask the assistant to explain the recipe before applying it, and use fictional data only.

## What you will learn

- Turn an idea into specific tables and fields.
- Find schema, sample data, and database change files.
- Ask AI to explain the impact before changing data.
- Check that insert and list work and that data persists.

## Files you will create or update

| Example file | What it should include |
| --- | --- |
| **`docs/data/model.md`** | Data, fields, relationships, and important rules, with a fictional example. |
| **`apps/api/src/db/schema.ts`** | One simple table with the agreed fields. |
| **`apps/api/drizzle/0001_records.sql`** | A database change generated by the project's tool. |
| **`apps/api/src/db/seed.ts`** | A few fictional records to test and show the list. |
| **`apps/api/src/app.test.ts`** | Tests that confirm a record is inserted and appears in the list. |

A migration is a file that applies a database change repeatably. Generate it with Drizzle Kit, the tool that prepares these changes, and review it before applying it. Do not delete or recreate data to make a test pass.

## Step-by-step exercise

1. Choose one type of record: an appointment, article, or ticket. Start with one table and a few fields.
2. Draw the table on paper. Explain what each field is for, whether it can be missing, and how it is checked when inserting.
3. Update the schema and generate a migration. Ask AI to explain what changes and which data might be affected.
4. Add fictional examples to the sample data file, called a seed.
5. Check that the app inserts a record, returns the list, and keeps the data after the page is refreshed. Make sure invalid input is not saved.
6. Review the schema and migration with someone from API or QA.
7. If there is time, decide whether to add update or delete. Ask QA to review those changes before the demo.

## Prompt for Codex or Claude

> I am responsible for Data/database on a beginner team. Read README.md, AGENTS.md, the brief, and the data model. This app is built from scratch. Propose one table with the agreed few fields and the minimum files for inserting records and returning the list. Include or update `docs/data/model.md` and explain each file. Wait for the team to review the plan. Then create the schema, migration, and a few fictional records. Add an insert-and-list check, and verify that data remains after refreshing the page. Do not add relationships or more tables without a clear need.

## Result and team review

Another person can explain what the table stores, insert a record, see it in the list, and confirm the data is still saved after refreshing the page.
