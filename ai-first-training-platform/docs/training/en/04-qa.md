# 04 · Review, check, and prepare the project for the next team

> Week 4 · 2 hours · Everyone participates

The minimum deliverable is a web app the team built from scratch. It must let someone insert a record with a form and list saved records from the database. It is ready when another person can install it, start it, try those two features, and continue the work using information in the repository. Updating and deleting are optional; check them only if the team added them.

## Before you start: check and ask for review

- A **test** is a check you can repeat, such as confirming that a form shows a message when a field is missing.
- A **pull request** is a proposed change someone else reviews before it becomes part of the team's work.
- **CI** is a set of automatic checks the repository runs, for example, when a change is proposed.
- A **handoff** is a written summary that lets someone else take over the project.

Use the README commands. If you do not understand a result, share it with the assistant and ask for an explanation; do not say a check passed unless you saw the result.

## What you will learn

- Turn each criterion into a check another person can repeat.
- Review files and effects on other parts of the project.
- Keep instructions, responsibilities, and decisions up to date.
- Check whether another team can set up the project and find the next task without an oral explanation.

## Requirements for every pull request

Each change ends with a review and a short handoff in the pull request. Do not repeat the whole project history; leave the information another person needs to understand and continue this change.

    Purpose and criterion met:
    Important decision and changed files:
    Checks run and observed results:
    Limits, risks, or checks still pending:
    Next step and related documentation:

The program requires CI on every pull request for format, lint, types, tests, and build; the repository must also use the organization's approved secret scanning. The human reviewer checks the diff, criteria, and evidence. The repository owner configures the main branch to require a pull request, successful CI, and one approval. If the team lacks access to enable these rules, record and escalate the blocker; the closeout criterion is not met yet.

## Files you will create or update

| File | What it should include |
| --- | --- |
| **`docs/qa/test-cases.md`** | Setup, action, expected result, and observed result for each case. |
| **Web and API tests** | Main cases, errors, and limits. Update existing tests that already cover the workflow. |
| **`docs/delivery/handoff.md`** | Status, startup and demo instructions, checks and their results, known limits, next steps, and role backups. |
| **`README.md`** | Requirements and commands a new person needs to install, start, and check the project. |
| **`AGENTS.md`** | Current map, technologies, and limits. Update it if folders or working rules change. |
| **`docs/team/assignments.md`** | Owners and backups for each area; who coordinates QA in the next stage. |
| **`docs/backlog/`** | Small pending tasks, with criteria, likely files, and priority. |
| **`.github/workflows/ci.yml`** | Required CI workflow for the program: run the real format, lint, type, test, and build commands. Use the equivalent for the approved platform if it is not GitHub. |
| **`.github/pull_request_template.md`** | Per-change handoff template: purpose, decision, checks and results, limits, and next step. |

Use paths that already exist in the repository. Do not create empty folders or duplicate existing documents.

## What to write in the handoff

Complete `docs/delivery/handoff.md` so someone who missed the meetings can get started:

```text
# Project handoff
Current status: insert form, record list, and optional improvements:
How to install and start (actual README commands):
How to run the demo and which practice data to use:
Where the screen, API, contracts, and data live:
Checks run and observed results:
Limits, known errors, and pending decisions:
Next tasks (criteria and likely files):
Owner and backup for each area:
Last updated:
```

Write actual results, including failures. Do not include keys, tokens, real data, or personal computer paths. If an important decision changed the design, say why and link to the relevant architecture note.

## Step-by-step exercise

1. Read each criterion and write a specific test for it.
2. Insert a record with valid information and check that it appears in the list.
3. Refresh the page and check that the record is still saved. Try an empty or invalid form and confirm it shows a clear message.
4. Check that an empty list also shows a clear message. If the team added update or delete, test those features too.
5. Run the commands listed in the README. Record the command, the result you saw, and anything you could not check.
6. Review someone else's change. Compare the result with the criteria; check the messages, keyboard use, and that the data is fictional.
7. Update README, AGENTS, role assignments, the backlog, and handoff to describe the current state.
8. **Run a transfer test.** Give a clean copy of the repository to another person or team without dictating the steps. Ask them to follow the README, start the app, insert a record, check that it appears in the list, find the relevant files, and choose a pending task. Record where they had questions.
9. Improve the documentation based on what the other team found. In the pull request, explain the criteria, changed files, and actual checks. Ask someone other than the author to review it, respond to their comments, and follow the repository's rules to merge it. Then prepare a demo someone else can repeat.
10. **Prepare reusable material for the next team.** Extract a repository structure and general rules, CI, and pull request template. Remove practice data and project-specific decisions. Ask the program owner to publish it as an approved template; if the team cannot create one, deliver the package and record who will follow up.

## Prompt for Codex or Claude

> I am responsible for QA/delivery on a beginner team. Read README.md, AGENTS.md, the criteria, backlog, and changed files. Help me prepare test cases and a Markdown handoff draft with status, instructions, paths, limits, and next steps. Leave test results blank until a person runs the checks. Check that the commands exist in README. Do not invent results or fill in information you cannot find: mark questions for the team to confirm. Suggest how a new person can test setup and find a task without expanding scope.

## Result and team review

Someone from another group can follow the instructions, insert a record, see it in the list, and explain how it was checked. If the team added update or delete, they can try those too. If they need information only the original team knows, record that gap and update the documentation before closing delivery.
