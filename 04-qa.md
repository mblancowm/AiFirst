# Module: Shared QA and Delivery

## Goal

Verify application behavior, AI answer quality, integration between roles, and readiness for a short live demo.

## Key idea

Every AI-generated change needs human review. A green build is necessary but does not prove the feature is correct or that an AI answer is supported by the source notes.

## Review and CI baseline

- Require pull requests to merge into protected `main`.
- Require at least one human review and a green CI run.
- Use `CODEOWNERS` so the owner of each role’s folder reviews its changes.
- Run lint, automated tests, and build on each pull request.
- Keep secrets out of Git; use secret scanning and approved server-side configuration.
- Review every AI-generated change and ask the author to explain what it does.

## Test layers

### Unit tests

Test request validation, project-scoped source selection, response mapping, and insufficient-evidence behavior. Use a fake AI service so tests are repeatable.

### Integration tests

Test database migrations, API persistence, and the end-to-end API contract with a test database. Verify that a project cannot read another project’s sources.

### UI tests

Test form validation and the empty, loading, answered, insufficient-evidence, and error states with mocked API responses.

### AI evaluation

Create at least ten sample questions, including:

- A question answered by one note.
- A question requiring two notes.
- A question missing from the available notes.
- A question that attempts to use another project’s information.

For each question, record expected evidence, returned source references, and whether the answer is supported. Repeat the evaluation after prompt or retrieval changes.

## Weekly QA rhythm

- **Week 1:** verify repository protections, agent guidance, and CI baseline.
- **Week 2:** check API/data contracts and test migrations and sample data.
- **Week 3:** run the integrated flow and begin the AI evaluation set.
- **Week 4:** finish regression checks, cross-role review, demo rehearsal, and retro.

## Codex prompt

> Read `AGENTS.md`, the linked feature plan, and the pull request diff. Review this change for correctness, security, test coverage, and consistency with the approved API/data contracts. Focus on concrete defects and missing tests. Do not approve or merge the change. Summarize findings by severity and explain any checks I should run manually. I will make the final review decision.

## Demo gate checklist

- A user can create a project and add source notes.
- A user can ask a question and see a source-grounded answer.
- Missing evidence is handled without invented details.
- Tests and CI pass, and all code has human review.
- No cross-project source leakage occurs in the tested flow.
- A five-minute demo can be run from a clean setup.
- Each developer can explain their layer and one design decision.
- `docs/retro.md` records what worked with AI, what did not, and what reusable skill or template the team created.

## Track for the retro

Record hours per developer per week, pull requests merged, pull requests returned for rework, and the team’s estimate of AI-generated code. Use these as learning signals alongside quality and explainability; do not treat code-generation percentage as a standalone measure of success.
